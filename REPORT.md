# sentiment-reviews: полный отчёт

Краткая версия для знакомства: [README](../README.md).

Предсказание оценки (1–5 звёзд) по тексту русскоязычного отзыва на организацию. Датасет: Яндекс Geo Reviews 2023 (500 000 отзывов, лицензия MIT). Проект построен как воспроизводимый эксперимент: аудит данных, split без утечек, честный бейзлайн, дообучение трансформера, учёт всех запусков в одной таблице.

> Фазы 0–6 завершены (данные, split, бейзлайн, rubert-tiny2, анализ ошибок, калибровка, сервис с API и Docker).

## Коротко

- **Split по группам.** Отзывы делятся по нормализованному названию организации: 54% отзывов относятся к сетям с несколькими адресами, и при случайном разбиении отзывы одной сети попали бы и в train, и в test. Проверки утечек пройдены.
- **Результат.** На test rubert-tiny2 лучше TF-IDF-бейзлайна: macro-F1 0.560 против 0.515, MAE 0.183 против 0.271. Но модели обучались в разных условиях (объём данных, веса классов, устройство), и при равных условиях разрыв заметно меньше (см. «Как читать это сравнение»).
- **Трудные классы.** Оценки 2–4★ остаются главной трудностью у обеих моделей (F1 0.2–0.45), оценки 1★ и 5★ распознаются хорошо.
- **Выбор метрики.** Веса классов повышают macro-F1 у бейзлайна, но ухудшают MAE; выбор зависит от того, что важнее.
- **Ошибки.** Около 75% ошибок трансформера приходятся на соседний класс; главные потери: четвёрки, уходящие в пятёрки, и двойки, уходящие в единицы. Ансамбль из трёх seed'ов не даёт значимого выигрыша на test.
- **Калибровка.** Вероятности трансформера переуверены (ECE 0.048); температурное масштабирование, подобранное только на val, снижает ECE до 0.018 на test, не меняя предсказаний.
- **Сервис.** REST API (FastAPI) и Docker-образ на CPU: p50 одиночного запроса около 6–8 мс, ответы контейнера совпали с сохранёнными предсказаниями на 500 отзывах val.

## Задача и метрики

Пять классов, сильный дисбаланс: после чистки 78.1% отзывов имеют оценку 5. Поэтому одной accuracy мерить нельзя: константа «всегда 5» даёт accuracy 0.781, но macro-F1 всего 0.175.

- **macro-F1** по пяти классам: основная метрика.
- **MAE** по шкале 1–5 и **QWK**: насколько ошибка близка к истинной оценке.
- accuracy приводится для справки.

## Данные и защита от утечек

- Датасет: [yandex/geo-reviews-dataset-2023](https://github.com/yandex/geo-reviews-dataset-2023), поля `address`, `name_ru`, `rubrics`, `rating`, `text`. Колонки с датой в данных нет.
- Очистка (500 000 → 498 663 строки): убраны оценка 0 (вне шкалы), строки без названия организации, тексты с конфликтующими оценками, точные дубликаты текста. Выбросы по длине не удаляются, длинные тексты обрезаются параметром `max_length`. Подробности: `reports/data_audit.md`.
- **Split v1 по группам:** 70 / 15 / 15 (351 249 / 72 662 / 74 752 отзыва), группа = нормализованное название организации, seed 42. Группировка по названию (а не по названию с адресом) нужна, потому что 54% отзывов относятся к сетям с несколькими адресами, и иначе отзывы одной сети попали бы в разные части.
- Проверки (`reports/leakage_report.md`): ни одна группа и ни один точный дубль текста не лежат в разных частях; близкие дубликаты (MinHash) есть у 0.04–0.06% отзывов, это в основном короткие шаблонные фразы, дополнительная чистка не нужна. Распределения классов по частям отличаются не более чем на 0.31 п.п.
- Test используется один раз на модель для оценки: она доступна только через явный флаг, повторный запуск блокируется. После финальной оценки test использовался ещё трижды, и ни разу для выбора модели или параметров: повторный прогон бейзлайна ради сохранения предсказаний (метрики воспроизвелись), разбор ошибок для подтверждения выводов, сделанных на val, и проверка калибровки с температурой, подобранной на val.
- Известный риск: 1.89% отзывов прямо упоминают оценку («поставлю 5»), причём упомянутое число совпадает с реальной оценкой лишь в 68% случаев. Эти отзывы из данных не удалялись; их разбор приведён в разделе «Анализ ошибок» (там использована другая эвристика, цифры немного отличаются).

## Модели

**Бейзлайн:** TF-IDF по словам (1–2-граммы) и по символам (`char_wb`, 2–5) + LogisticRegression, `class_weight=balanced`, 100k обучающих отзывов. Конфигурация выбрана на val из шести вариантов (слова / символы / оба × без весов / balanced), размер train выбран по learning curve по правилу, заданному до запуска (`configs/baseline.yaml`). Кривая (val, среднее по 3 подвыборкам): macro-F1 0.481 при 10k, 0.521 при 100k, плато не достигнуто.

**rubert-tiny2** (`cointegrated/rubert-tiny2`, 29.2 млн параметров): полное дообучение, `max_length=256`, динамический паддинг, lr 1e-4, 3 эпохи, batch 32, `class_weight=none`, полный train (351k), 3 seed'а (42, 123, 2026). Lr и `class_weight` выбраны небольшим перебором (6 запусков, 50k train, val). Обучение на GPU (RTX 4060 Laptop, bf16).

## Результаты (test)

| Модель | Macro-F1 | MAE | Accuracy | QWK |
|---|---|---|---|---|
| Константа «всегда 5» | 0.176 | 0.517 | 0.782 | 0 |
| TF-IDF + LogReg (100k, balanced; 1 запуск) | 0.5147 | 0.2706 | 0.8061 | 0.8214 |
| rubert-tiny2 (351k, без весов; 3 seed'а, mean ± std) | **0.5600 ± 0.0037** | **0.1834 ± 0.0010** | 0.8647 ± 0.0002 | 0.8788 ± 0.0014 |

Для константы значения пересчитаны на составе test (78.2% пятёрок); в разделе «Задача» приведены значения для всех данных (78.1%).

F1 по классам (test):

| Модель | 1★ | 2★ | 3★ | 4★ | 5★ |
|---|---|---|---|---|---|
| TF-IDF + LogReg | 0.71 | 0.20 | 0.32 | 0.42 | 0.92 |
| rubert-tiny2 | 0.76 | 0.23 | 0.40 | 0.45 | 0.95 |

Средние оценки (2–4★) остаются главной трудностью у обеих моделей.

### Как читать это сравнение

Модели в таблице различаются не только архитектурой:

1. **Объём обучения:** 100k у бейзлайна против 351k у трансформера.
2. **`class_weight`:** `balanced` у бейзлайна, без весов у трансформера. Это сильно влияет на MAE: на 50k у rubert-tiny2 MAE 0.20 без весов и 0.26 с весами при почти равном macro-F1 (0.531 и 0.527, разница в пределах шума).
3. **Устройство обучения:** GPU у трансформера, CPU у бейзлайна.

Сравнение при равных условиях (50k train, `balanced`, val): бейзлайн macro-F1 0.509 / MAE 0.269 (3 подвыборки, std 0.002), rubert-tiny2 0.527 / 0.255 (один seed). Выигрыш трансформера реален, но заметно скромнее, чем разрыв в таблице выше.

### Стоимость инференса (CPU, 24 потока)

| | Размер | Время, с / 1000 отзывов | Задержка 1 запроса (p50 / p95) |
|---|---|---|---|
| TF-IDF + LogReg | 35.6 МБ | 1.05 (одним батчем) | 13.3 / 18.6 мс |
| rubert-tiny2 | 119 МБ | 1.10 (batch 32) | 5.4 / 8.3 мс |

Замеры грубые: оба по 1000 отзывам val (задержка по 300 отдельным запросам), время включает токенизацию или векторизацию; число потоков у бейзлайна не фиксировалось. Раньше время бейзлайна на всём test оценивалось в 0.50 с / 1000 отзывов; методики разные, сопоставлять их нельзя. На GPU трансформер обрабатывает 1000 отзывов за ~0.2 с. Таблица со всеми цифрами: `reports/tables/model_comparison.md`.

TF-IDF (слова + символы) + LogReg, `class_weight=balanced`, метрики на val, среднее ± std по 3 независимым подвыборкам train (словарь обучается отдельно на каждой подвыборке). Обучение на CPU.

|---|---|---|---|---|
| 10k | 0.4810 ± 0.0014 | 0.2904 ± 0.0024 | 10 с | |
| 25k | 0.4979 ± 0.0020 | 0.2781 ± 0.0013 | 29 с | |
| 50k | 0.5094 ± 0.0019 | 0.2691 ± 0.0010 | 65 с | |

![Learning curve](../reports/figures/learning_curve.png)

Каждое удвоение выборки даёт около +0.011 macro-F1 и около −0.010 MAE, что заметно больше разброса между подвыборками. Правило выбора размера было задано до запуска (прирост следующего шага меньше максимума из std между повторами и 0.005); оно не сработало, поэтому взят наибольший проверенный размер. 100k это нижняя оценка возможностей бейзлайна, а не оптимум. Кривая относится к TF-IDF и ничего не говорит об оптимальном объёме данных для трансформера.

## Как ошибается бейзлайн (test)

![Матрица ошибок бейзлайна на test](../reports/figures/baseline_confusion_test.png)

- 74% ошибок приходятся на соседний класс; грубые ошибки на 3–4 класса составляют 9% (1 310 из 14 498).
- Самая частая ошибка: 5 509 пятёрок (9.4% всех пятёрок) предсказаны как четвёрки, это 38% всех ошибок. По-видимому, это цена `class_weight=balanced`: recall четвёрок 0.56 при precision 0.33.
- Двойки распознаются хуже всего: верно только 19%, а 41% двоек модель считает единицами.

## Анализ ошибок бейзлайна и трансформера

Разбор сделан на val и подтверждён на test; выводы не менялись. Интервалы получены бутстрэпом по группам (`group_key`), потому что отзывы об одном месте зависимы. Все таблицы: `reports/error_analysis_val_tables.md`, `reports/error_analysis_test_tables.md`, выводы: `reports/error_analysis.md`. Ниже трансформер означает seed 42 (macro-F1 0.5627 на test; в основной таблице среднее по трём seed'ам 0.5600).

- **Разница моделей значима.** Macro-F1 трансформера выше бейзлайна на 0.048 (95% ИИ 0.041–0.055 на test; 0.047 на val). Напомним, что условия обучения различаются (см. «Как читать это сравнение»).
- **Ансамбль не окупается.** Среднее вероятностей трёх seed'ов даёт +0.001 к одиночной модели на test (ИИ −0.003…+0.006, незначимо; на val +0.006 на границе значимости). Для сервиса достаточно одной модели.
- **Потери сосредоточены на соседних классах.** Около 75% ошибок на 1 балл, поэтому QWK высокий (0.88) при скромном macro-F1. Класс 5 это 78% данных (F1 0.95); макро-метрику тянут вниз 2★, 3★ и 4★.
- **4★ уходят в 5★.** У трансформера без весов recall четвёрок 0.41 (45% четвёрок предсказаны как 5★), у бейзлайна с `balanced` 0.56 при precision 0.33 (у трансформера 0.50). Бейзлайн верен там, где трансформер ошибается, на классе 4 чаще (1 536 против 632 случаев «верен только один из двух»), на пятёрках наоборот (280 против 5 323).
- **2★ распознаются хуже всего** (recall около 0.19 у обеих моделей): примерно 40% двоек обе модели считают единицами.
- **Часть ошибок не исправима по тексту.** Среди уверенных общих ошибок (обе модели ≥ 0.99) много явно положительных отзывов с оценкой 4 («Всё супер, рекомендую») и несколько положительных отзывов с оценкой 1, похожих на шум меток. Это впечатление по 12 просмотренным примерам. Обе модели ошиблись на 9.6% test; выбирая всегда верную из двух, можно было бы получить accuracy около 0.90 против 0.865, но это нереализуемая верхняя граница.
- **Длина.** Accuracy падает на длинных отзывах: у трансформера 0.89 на 100–199 символов и 0.74 на 800+ (бейзлайн: 0.84 и 0.67). Причина не проверялась; возможно, играют роль смешанный тон и обрезка по `max_length=256`.
- **Прямое упоминание оценки** (2.2% отзывов, эвристика, вручную не проверена). Когда число в тексте совпадает с меткой, F1 трансформера 0.80 против 0.58 у бейзлайна: трансформер лучше использует явные подсказки. В 39% найденных случаев число не совпадает с меткой, там точность обеих моделей около 0.55; это шум меток или ложные срабатывания эвристики.
- **Эмодзи и рубрики.** Accuracy выше у отзывов с эмодзи (0.93 против 0.86) и в рубриках вроде салонов красоты, стоматологий и автосервисов (0.92–0.96), хуже в магазинах и торговле (0.78–0.80). Это, вероятно, отражает состав классов (почти все пятёрки), а не качество модели; причинной связи не показано. Срезы сравнивать нужно по accuracy и MAE, не по macro-F1.

## Калибровка

Бейзлайн откалиброван хорошо (ECE 0.035 на test), трансформер переуверен (ECE 0.048): на val при уверенности 0.8–0.9 он верен в 71% случаев, а 72% его предсказаний имеют уверенность ≥ 0.95 при заявленных 99% и фактической точности 97%. Температурное масштабирование (`softmax(log p / T)`, один параметр на модель, T подобрана только на val) не меняет предсказаний, а значит accuracy и macro-F1, но исправляет вероятности:

| Модель | T | ECE val: до → после | ECE test: до → после | log-loss test: до → после |
|---|---|---|---|---|
| TF-IDF + LogReg | 0.844 | 0.037 → 0.014 | 0.035 → 0.014 | 0.533 → 0.527 |
| rubert-tiny2 (seed 42) | 1.351 | 0.048 → 0.021 | 0.048 → 0.018 | 0.398 → 0.373 |
| Ансамбль (3 seed'а) | 1.300 | 0.038 → 0.014 | 0.039 → 0.014 | 0.377 → 0.360 |

Температура, подобранная на val, переносится на test без потерь. Небольшая переуверенность у трансформера остаётся (средняя уверенность 0.874 при accuracy 0.865). Значения T сохранены в `reports/calibration.json`; сервис должен отдавать откалиброванные вероятности.

## Сервис: REST API и Docker

Сервис отдаёт оценку 1–5 по тексту отзыва: rubert-tiny2 (seed 42) на CPU с температурной калибровкой (T = 1.3507 из `reports/calibration.json`). Параметры берутся из `configs/transformer.yaml` и `reports/calibration.json`, то есть из тех же файлов, что и при оценке; переопределяются переменными окружения (`MODEL_DIR`, `MAX_LENGTH`, `DEVICE`, `TORCH_THREADS`).

| Метод и путь | Назначение |
|---|---|
| `GET /health` | живость и готовность модели |
| `GET /info` | модель, T, `max_length`, устройство, число потоков |
| `POST /predict` | `{"text": "..."}` → оценка и вероятности |
| `POST /predict/batch` | `{"texts": [...]}` (до 64) → предсказания в том же порядке |

Ответ содержит `rating`, откалиброванные `probabilities` по классам 1–5, `confidence`, `expected_rating` и флаг `truncated` (отзыв длиннее 256 токенов и был обрезан). Пустой или состоящий из пробелов текст, текст длиннее 20 000 символов и батч больше 64 дают HTTP 422. Формат ответа (значения иллюстративные):

```json
{"rating": 5, "confidence": 0.91, "expected_rating": 4.8,
 "probabilities": {"1": 0.01, "2": 0.01, "3": 0.02, "4": 0.05, "5": 0.91}, "truncated": false}
```

```bash
python -m uvicorn src.serving.app:app --port 8000          # локально
docker build -t sentiment-reviews .                        # образ; нужны веса models/rubert-tiny2/seed_42
docker run --rm -p 8000:8000 sentiment-reviews
```

Веса в репозиторий не входят, поэтому перед сборкой образа их нужно получить (`python -m src.models.transformer --final`). Образ самодостаточный: веса копируются внутрь, сеть при запуске не нужна. Размер образа 1.95 ГБ на диске (476 МБ в сжатом виде).

**Проверка соответствия.** `python -m src.serving.check_parity` сравнивает ответы запущенного сервиса с сохранёнными предсказаниями seed 42 на val. На 500 случайных отзывах контейнер дал те же оценки (расхождений 0), максимальная разница вероятностей: медиана 0.0003, p95 0.0017, максимум 0.0053. Остаточная разница объясняется тем, что метрики считались на GPU со смешанной точностью, а сервис считает на CPU в fp32 (плюс округление ответа до 4 знаков).

**Скорость** (`python -m src.serving.benchmark`; 300 последовательных запросов и по 10 батчей каждого размера, тексты из val, клиент и сервер на одной машине, задержка включает HTTP, токенизацию, инференс и калибровку):

| | Локально (24 потока) | Docker (2 потока) |
|---|---|---|
| `/predict`, p50 / p95, мс | 7.8 / 10.8 | 6.1 / 11.2 |
| `/predict/batch`, текстов/с, батч 1 | 107 | 140 |
| батч 8 | 305 | 225 |
| батч 32 | 220 | 133 |
| батч 64 | 329 | 203 |

Задержка одиночного запроса в контейнере не хуже локальной; пропускная способность больших батчей ниже, что согласуется с тем, что контейнеру выделено 2 потока (локальный запуск шёл на 24 потоках torch). Различия между размерами батча немонотонны и получены по малому числу повторов, поэтому как закономерность их читать нельзя. Сопоставлять эти цифры с замером модели без сервиса (`transformer_cost.json`, 1000 отзывов одним вызовом) нельзя: там другая постановка.

Замеры клиентских скриптов делаются с отключённым системным прокси (`trust_env=False`): на одной машине запрос к адресу сервиса через `httpx` с настройками по умолчанию получал HTTP 503 с пустым телом, хотя `curl` получал корректный ответ. Причина не установлена.

## Неожиданные результаты

- **Веса классов по-разному действуют на две модели.** У бейзлайна `balanced` даёт +0.04 macro-F1 (0.465 → 0.507 на 50k, val) ценой роста MAE (0.228 → 0.269). У rubert-tiny2 macro-F1 почти не меняется (0.531 и 0.527), а MAE ухудшается (0.20 → 0.26).
- **Learning curve бейзлайна не насытилась** даже на 100k, поэтому честный верхний предел TF-IDF здесь не измерен.
- **MAE бейзлайна на test хуже, чем на val** для той же обучающей подвыборки: 0.2706 против 0.2581, при почти одинаковом macro-F1 (0.5147 против 0.5167). Причина не выяснена. Возможное объяснение: крупные сети целиком попадают в одну из частей split и сдвигают состав; это не проверялось.
- **Разрыв в основной таблице преувеличивает выигрыш трансформера**: при равных условиях он заметно меньше (см. «Как читать это сравнение»).
- **Бейзлайн на одном запросе медленнее трансформера** (p50 13.3 мс против 5.4 мс), хотя модель втрое меньше (36 МБ против 119 МБ), а пакетом оба обрабатывают 1000 отзывов примерно за секунду. Вероятная причина: векторизация символьных n-грамм на каждый запрос; не профилировалась.
- **Калибровка у моделей противоположна:** бейзлайн слегка недоуверен (T = 0.84), трансформер переуверен (T = 1.35).

## Воспроизведение

Нужен Python 3.10+. Трансформер обучался на GPU; бейзлайн и все проверки работают на CPU.

```bash
git clone https://github.com/kankul-23/sentiment-reviews
cd sentiment-reviews
python -m venv .venv
.venv\Scripts\activate            # Linux/macOS: source .venv/bin/activate

# PyTorch ставится отдельно под ваше железо (CPU или CUDA): https://pytorch.org
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
pytest
```

Датасет скачать вручную из [yandex/geo-reviews-dataset-2023](https://github.com/yandex/geo-reviews-dataset-2023) и положить `geo-reviews-dataset-2023.tskv` в `data/raw/` (имя файла задано в `configs/data.yaml`).

```bash
# Фазы 1-2: очистка, проверки
python -m src.data.audit            # -> data/processed/reviews_clean.parquet, reports/data_audit.md
python -m src.data.leakage          # проверки утечек (несколько минут) -> reports/leakage_report.md
```

Готовый split лежит в репозитории (`data/splits/split_v1.*`), поэтому `python -m src.data.splitting` на готовом клоне откажется перезаписывать его: так защищён test. Проверка `leakage` заодно сверяет хэш test-части с сохранённым и покажет, если очищенные данные не совпадают со split.

```bash
# Фаза 3: бейзлайн
python -m src.models.baseline                      # сравнение конфигураций на val
python -m src.evaluation.learning_curve            # learning curve
python -m src.models.baseline --final              # финал на test, один раз

# Фаза 4: rubert-tiny2
python -m src.models.transformer --check-tokens    # токенайзер, длины
python -m src.models.transformer --bench           # замер скорости
python -m src.models.transformer --search          # lr x class_weight на val
python -m src.models.transformer --final           # 3 seed'а, test
python -m src.models.transformer --cost            # размер, задержка на CPU
python -m src.evaluation.comparison                # итоговая таблица

# Фаза 5: предсказания, разбор ошибок, калибровка
python -m src.models.baseline --save-predictions   # вероятности val/test, модель, стоимость бейзлайна
python -m src.evaluation.error_analysis            # разбор на val
python -m src.evaluation.error_analysis --split test --allow-test   # подтверждение на test
python -m src.evaluation.calibration               # температура на val
python -m src.evaluation.calibration --allow-test  # проверка на test

# Фаза 6: сервис (отдельный терминал: сервис запущен на :8000)
python -m src.serving.check_parity --url http://localhost:8000   # совпадение с сохранёнными предсказаниями
python -m src.serving.benchmark --url http://localhost:8000     # задержка и пропускная способность
```

Каждый запуск пишет строку в `reports/experiments.csv` (фаза, модель, параметры, seed, часть данных, метрики, время). Скрипты Фазы 5 пишут результаты в `reports/`, но не в журнал (`--save-predictions` переобучает бейзлайн с той же конфигурацией и сверяет метрики с финальной оценкой). Веса моделей (`models/`) и предсказания (`data/predictions/`) в репозиторий не входят.

## Ограничения

- У бейзлайна один запуск на test, без оценки разброса по seed'ам.
- Число эпох трансформера не перебиралось; лучший lr лежит на краю сетки (1e-4).
- Замеры времени и памяти получены на одной машине (ноутбук) и приблизительны.
- Выводы о срезах (длина, эмодзи, рубрики) описательные: причины не проверялись, в частности не измерена доля отзывов, обрезанных по `max_length`.
- Эвристика «прямое упоминание оценки» не проверена вручную, поэтому доля несовпадений (около 39%) смешивает шум меток и ложные срабатывания.
- Низкий recall четвёрок у трансформера не исправлялся (пороги и приоры классов не подбирались), смешивание вероятностей двух моделей не пробовалось.
- Температура подобрана на val и проверена на test для одного сплита и одного набора seed'ов; для ансамбля она относится к усреднённым вероятностям.
- Сервис проверен на CPU, в одном процессе, без нагрузочного теста с параллельными запросами; прямые проходы идут по одному (блокировка), авторизации и ограничения частоты нет.
- Замеры сервиса сделаны на одной машине, в Docker Desktop (2 потока torch), по малому числу запросов; для другого железа цифры будут другими.
- В образ входит одна модель (seed 42) и её температура; смена модели требует пересчёта T (`python -m src.evaluation.calibration`).
- Версии зависимостей образа зафиксированы (`requirements-serving.txt`, `torch==2.14.1` в Dockerfile), но базовый образ `python:3.11-slim` указан тегом, а не дайджестом.
- ruBERT-base (опциональный пункт плана) в сравнение не вошёл; других моделей, кроме двух в таблице, нет.
- Оценка относится к одному датасету (отзывы на Яндекс Картах за январь–июль 2023) и не проверялась на других источниках.
- Группировка по названию не склеивает варианты написания («Магнит у дома» и «Магнит»), поэтому небольшая остаточная утечка между сетями возможна; её размер не измерялся.
